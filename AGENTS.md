# Darve frontend working instructions

- Read [PLAN](docs/PLAN.md), [ARCHITECTURE](docs/ARCHITECTURE.md) and the relevant owning standards before changes. Continue the user's current authorized batch; a backlog row is not permission to implement every feature.
- Preserve the selected UI/UX and historical folders. User-approved redesign scope supersedes reference designs; do not invent new product rules. Keep the original backend checkout and persistent development database untouched unless backend changes are explicitly in scope.
- `app/` bootstraps. `routes/` composes. `features/` owns business UI. `entities/` holds pure domain models. `services/` owns external infrastructure. `design-system/`, `motion/` and `shared/` have separate responsibilities. Follow enforced dependencies and explicit slice entries. Never disable architecture rules to finish a feature.
- Use backend public contracts and authoritative state. No fake login, localStorage tokens, simulated checkout, fabricated money/coin results, frontend authorization promises or invented endpoints. Creator, staff, guest receipt and overlay grants have distinct authority.
- Keep React state local, backend state in TanStack Query, filters/navigation in the URL. No global store or form framework until a concrete requirement justifies it. No duplicated ledger/funding state.
- Import GSAP/Framer Motion only in `motion/`; expose narrow adapters. Respect reduced motion; scope and clean up GSAP. Never attach business side effects to animation completion or let two engines animate the same property on the same element.
- Render viewer/provider text as text. Keep secrets, session/grant URLs, donor data and raw provider payloads out of logs, Git, screenshots and traces. Do not add analytics or external reporters without reviewed data handling.
- Reuse existing backend feature owners for defects. Update the owning record and [PLAN](docs/PLAN.md) once; do not copy progress history throughout docs. Keep implemented, verified, planned and externally blocked work distinct.
- Verify focused changes while iterating; run `npm run check` and relevant Playwright acceptance when code settles. Do not substitute mocked tests for actual backend/provider acceptance. Record failures and limitations. Changes to architecture enforcement require rejection/acceptance regression cases.
- Use focused branches and reviewable commits. Publish PRs to protected `dev` only when a remote/review workflow is established; release via reviewed `dev` → `main`. No remote exists at bootstrap. Do not invent successful hosted CI, branch protections or release authorization. Never force/reset/discard unrelated work. Keep hooks active; CI independently repeats mandatory gates.
- Follow the deployment-preparation checklist in [OPERATIONS](docs/OPERATIONS.md) when deployment becomes in scope. Resend is the chosen staff email provider, configured server-side. Local-first sequencing does not waive deployment/activation gates.
