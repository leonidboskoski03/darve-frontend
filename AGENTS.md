# Darve frontend working instructions

- Start with [CURRENT_STATE](docs/CURRENT_STATE.md), the relevant [tracker](docs/FRONTEND_TASK_TRACKER.md) row and [ARCHITECTURE](docs/ARCHITECTURE.md). Use the [docs index](docs/README.md) to select owning sections. Follow [WORKFLOW](docs/WORKFLOW.md); [PLAN](docs/PLAN.md) owns batch acceptance. Continue the user's current authorized scope; a backlog row is not permission to implement every feature.
- Preserve the selected UI/UX and historical folders. User-approved redesign scope supersedes reference designs; do not invent new product rules. Keep the original backend checkout and persistent development database untouched unless backend changes are explicitly in scope.
- `app/` bootstraps. `routes/` composes. `features/` owns business UI. `entities/` holds pure domain models. `services/` owns external infrastructure. `design-system/`, `motion/` and `shared/` have separate responsibilities. Follow enforced dependencies and explicit slice entries. Never disable architecture rules to finish a feature.
- Use backend public contracts and authoritative state. No fake login, localStorage tokens, simulated checkout, fabricated money/coin results, frontend authorization promises or invented endpoints. Creator, staff, guest receipt and overlay grants have distinct authority.
- Keep React state local, backend state in TanStack Query, filters/navigation in the URL. No global store or form framework until a concrete requirement justifies it. No duplicated ledger/funding state.
- Import GSAP/Framer Motion only in `motion/`; expose narrow adapters. Respect reduced motion; scope and clean up GSAP. Never attach business side effects to animation completion or let two engines animate the same property on the same element.
- Render viewer/provider text as text. Keep secrets, session/grant URLs, donor data and raw provider payloads out of logs, Git, screenshots and traces. Do not add analytics or external reporters without reviewed data handling.
- Reuse existing backend feature owners for defects. Update the owning record and [tracker](docs/FRONTEND_TASK_TRACKER.md) once; change PLAN only when scope/dependencies/acceptance change. Do not copy progress history throughout docs. Keep implemented, verified, planned and externally blocked work distinct. Update CURRENT_STATE only when capabilities/priorities/blockers change.
- Use the [new-chat template](docs/NEW_CHAT_TASK_TEMPLATE.md) and workflow restart procedure when switching/resuming work. Leave source/branch/build freshness, dirty files, checks, owned runtime cleanup and next action in the owning record; never rely on conversation-only memory or transferable tool sessions.
- Verify focused changes while iterating; run `npm run check` and relevant Playwright acceptance when code settles. Markdown-only work needs local link/changed-document format/diff checks; installed hooks/CI still apply. Do not substitute mocked tests for actual backend/provider acceptance. Record failures and limitations. Changes to architecture enforcement require rejection/acceptance regression cases.
- Follow [Git/CI setup](docs/GIT_AND_CI_SETUP.md) for focused branches, reviewable commits, current-head checks, release and verified task-branch cleanup. Use focused task PRs into dev with light hosted checks and dev → main only for a stable release with full frontend acceptance. Read actual remote/protection/CI evidence from the owning record; do not invent successful hosted checks or release authorization. Never force/reset/discard unrelated work. Keep hooks active; CI independently repeats mandatory gates.
- Follow [OPERATIONS](docs/OPERATIONS.md) and the [deployment-preparation checklist](docs/DEPLOYMENT_PREPARATION_CHECKLIST.md) when deployment becomes in scope. Resend is the chosen staff email provider, configured server-side. Local-first sequencing does not waive deployment/activation gates.
