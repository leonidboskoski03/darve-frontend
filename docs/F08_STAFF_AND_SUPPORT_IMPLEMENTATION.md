## What we will build

Creators get a private support area in their existing workspace: ticket list, account/challenge/stream ticket creation, retained conversation, unread state and owned context links. Staff get a separate portal: invitation/password/email-code entry, explicitly controlled availability, queue, assigned conversations, internal notes, authorized inspection and administration. Owner admins additionally get confirmed moderation, reassignment and audited recovery actions.

Use the established typography, tokens, fields, panels and restrained motion. The generic legacy contact form supplies visual cues only; its fake submission and extra contact fields do not define the ticket API. New staff layouts need a bounded screen proposal and responsive/keyboard review in their implementation task. Do not claim historical pixel parity for screens without a selected reference.

Out of scope: public complaints/refund support, attachments, typing/presence, chat posting, automatic refunds, coins/template administration (F09), live payments, deployment and real Resend delivery. No new global store or form framework is justified by this map.

## Staff sign-in and permission flow

Confirmed backend policy is `auth0-password-darve-email-otp-v1`: Auth0 verifies the password; Darve verifies a fresh emailed code for every new login. An Auth0 identity, callback URL or company email domain alone never establishes staff membership. The portal must not collect/store an Auth0 password or use creator OAuth as staff sign-in.

1. Read the staff session and, when applicable, pending email-code status from the staff API. Treat redirects/return hints as navigation only. Show signed-out, email-code-pending, enrollment-pending and authenticated states distinctly.
2. Explicit sign-in calls staff `auth/start`; sensitive-action reauthentication uses `auth/step-up`. Both return an ordinary v1 data object containing `authorizationUrl`, **without the creator start response's `expiresAt`**. Validate navigation and let the backend callback handle the code/state/issuer exchange.
3. Callback returns HTTP 303 to the configured staff frontend's fixed `/staff/verify-email` landing path while code verification is pending. This entry path is distinct from the four allowed final return paths in the login/verification contracts. Under the selected policy the callback establishes the browser-bound pending email-code cookie, not an authenticated session. Read email-code status for its current expiry and CSRF, then submit the eight-digit code. Resend/cancel use that pending flow's CSRF. Do not reset backend expiry/attempt limits with a frontend timer or claim resend success before the response.
4. Verification returns `authenticated` or `enrollment_pending` plus an allowlisted return path. Refetch session after the transition. For invitation enrollment, show the server role and require explicit acceptance with enrollment CSRF. The backend invitation URL uses `/staff/enrol#invitation=…`; consume and remove its fragment before mounting, keep it out of Query/storage, and never show it again through an automatic replay. Invitation creation can return its one-time acceptance URL; a replay may return null.
5. A staff session supplies role, permissions, membership revision, expiry, authentication time and staff CSRF. Writes require the exact staff frontend Origin and `x-staff-csrf` from the applicable pending/enrollment/session state. They do not use creator CSRF. Logout is a JSON acknowledgement, not 204.
6. On recent-assurance failure, retain only a safe action description, reauthenticate and refetch current authority/resource state. Require a fresh deliberate confirmation; never replay a privileged command automatically after step-up.

Development cookies are `darve_staff_dev_<kind>`; production uses `__Host-darve-staff-<kind>` for session/login/enrollment/email-code. They are HttpOnly, SameSite=Lax and path `/`, with Secure in production and no Domain attribute. JavaScript does not read their secrets.

## Conversation and realtime semantics

Tickets are private creator conversations in account/challenge/stream categories. Status is `open`, `in_progress`, `waiting_for_streamer` or `resolved`; a creator reply reopens the same ticket. A staff reply or internal note alone does not change status. Autoassignment uses eligible available staff with least active work; a claim is atomic, existing assignment is retained and owner-admin reassignment is explicit. No available staff leaves an unassigned queue item; do not promise an immediate reply.

Public replies/status use current public revision and staff authority revision where required; context commands use context revision. Notes/assignment use staff authority, and note read marks are separate. Queue metadata is not permission to preload a whole conversation. Internal notes must not affect creator responses, badges, timestamps or event hints.

`SupportMessage` can return `body:null, redacted:true`. Clear removed text from snapshots and mounted drafts on authoritative resync; never reconstruct it from an old cache. Page cursors are opaque, audience/actor/resource/authority-bound and expiring. A stale cursor is discarded and the current page refetched, not edited or reused for another ticket.

Backend `packages/domain/src/modules/support/application/support.ts` emits only `resync_required`, `changed` and `heartbeat`. Their data is a ticket ID, audience-specific revision and read/unread state; staff additionally receives note read/unread state. Both support controllers send `retry:` but **no event `id:` or replay cursor**. These hints contain no message text. They are not overlay v1/v2 snapshots and do not use the overlay Last-Event-ID/reducer contract.

F08-04/05 need a separately validated support Fetch/SSE adapter, bound to the correct audience and active conversation. Read current detail/history on initial connection, resync, change and reconnect. Bound retries and honor current server policy; abort on navigation, logout, expiry, access loss and backpressure. The server rechecks ticket authority while streaming. Reconcile HTTP reads through the same authority QueryClient, with late-result fences; a heartbeat never establishes new permissions.

## Moderation and recovery confirmation

The source domain validators require ban/unban action, reason, expected restriction version and confirmation binding target/action/version. Review flags bind target kind/ID and reason; transitions bind current version and explicit target/state/version confirmation. Legal transitions are open → in_review → resolved. SUPPORT may flag but cannot resolve; an open review does not automatically pause funding or require every challenge to be pre-reviewed.

A ban blocks new collection, acceptance and contributions without rewriting history. In-flight provider success can still reconcile. Do not present bans as refunds, deletion or recalled external checkouts. An unban does not reopen an expired funding window.

Recovery is owner-admin-only and **OFF by default**. Both commands bind the ticket, context, staff authority, funding and performance revisions plus a reason. Extensions additionally bind window revision and exact previous/new deadline confirmation; they must occur before the current effective deadline and obey configured increment/cumulative caps. Continuations confirm immutable original and verified owned replacement broadcast IDs. Neither rewrites the original accepted terms, original source or financial history.

The UI must show current and proposed effects, unchecked confirmation and relevant exact versions before submitting. The backend remains the deadline/policy/ownership authority. Numeric commercial limits are not agreed by this map; do not invent them. F04-G05 still owns pre-acceptance extension disclosure/policy projection. If recovery policy, eligible broadcast discovery or required authority facts are not available through a safe public contract, record the specific backend projection gap and keep the command unavailable. Do not import a repository/private adapter to make the form work.
